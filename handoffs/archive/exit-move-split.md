# Ashfall Handoff — Exit Split: Grid Travel vs. Here

Current shipped version: v0.4.3
Implied version-change type: PATCH
Issue: #18 — Split Move into grid travel (ordered by compass) and Here (everything else)

## What this is

Every exit currently renders as a Move button in `exits`-array authoring order.
This pass does two things: moves non-travel exits into the **Here** section, and
orders the street/block exits that remain by compass — North, East, West, South.

Rendering-only. The exits themselves are not touched: nothing in WORLD DATA is
reordered, renamed, or given a new field.

## Relevant existing state

Verified by driving an instrumented copy of the current `ashfall.html` in
headless Chromium and walking all 774 exits in the built world.

- `renderMoveActionsPanel()` (`ashfall.html:4738`) iterates
  `getExitsForRoom(room, roomId)` and appends one button per exit, in array
  order. Nothing sorts.
- `getExitsForRoom()` (`ashfall.html:3739`) filters `room.exits` by locked
  doors, then **appends** window-climb exits generated at runtime from
  `windows`. Those appended exits are not in `room.exits` and have no
  `doorId`.
- The world holds **218 rooms**, of which **176 are street/mid-block nodes**.
- **672 of 774 exits are grid travel**; the remaining 102 are everything else.

### Identifying a street node

Per the ROOM SCHEMA comment, street and mid-block rooms use their own room id
as their `locationId`. That test was checked against
`MAP_STREET_NODE_IDS` (the set `renderMapClose()` derives from `MAP_STREETS`):

- rooms where `locationId === roomId`: **176**
- ids in `MAP_STREET_NODE_IDS`: **176**
- in one set but not the other, either direction: **0**

The two are exactly equivalent. **Use `world[id].locationId === id`**, not
`MAP_STREET_NODE_IDS` — the former is intrinsic to WORLD DATA, while the latter
is map-rendering data, and movement should not depend on it (Project Guide, "no
duplicated source of truth").

### Why not the cross-Location test

Splitting on `fromRoom.locationId !== toRoom.locationId` sends **706** exits to
Move — 34 too many. It wrongly classifies `stairs1 ↔ stairs2`,
`cornerstore ↔ cornerstore_apt`, `pharmacy ↔ pharmacy_apt`,
`hardware ↔ hardware_apt`, `oak_stairs ↔ oak_hallway2`, `balcony → alley`
("Climb down the fire escape"), `water1st ↔ riverbank`,
`hallway1 → mid_poplar_1_2` ("Step outside"), and every "Enter the …" /
"Leave the …" building door. All of those belong in Here.

### Direction is already derivable

`computeDirection()` (`ashfall.html:3280`) applied to the two rooms'
`locationId`s reproduces the compass word in the exit's own label for **all 672
grid exits — zero mismatches, zero diagonal ties.** No label parsing is needed
and no new exit field is required.

### Shape of the grid exits

Grouping each street room's grid exits by computed direction:

| Exits in one direction bucket | Count |
|---|---|
| 1 (mid-block node) | 224 |
| 2 (intersection: "Head…" + "Step into the block…") | 224 |
| 3 or more | 0 |

Directions used: north 112, east 112, west 112, south 112 — exactly symmetric.
Only the four compass directions occur; no `up`/`down` appears among grid exits
(every street node is `z:0`).

In all 224 two-exit buckets, the "Head …"/"Continue …" exit already precedes
the "Step into the block …" exit in authoring order. **Zero exceptions.**

Move-button count per street room after the split:

| Buttons | Rooms |
|---|---|
| 2 | 112 |
| 4 | 4 |
| 6 | 24 |
| 8 | 36 |

Here-exit count on street rooms: **167 have none**, 7 have one, 2 have two. The
two sections do not compete for space.

### Markup

```html
<div class="actions-group"><h2>Move</h2><div class="actions" id="moveActions"></div></div>
<div class="actions-group" id="hereGroup" style="display:none;"><h2>Here</h2><div class="actions" id="hereActions"></div></div>
```

`hereGroup` carries an id and is hidden when empty by
`renderHereActionsPanel()` (`ashfall.html:4832`). The Move group has **no id**
and no hiding logic.

## Rules / mechanics

### 1. Classification

An exit is **grid travel** if and only if both its source room and its
destination room are street nodes:

```
isGridTravel(fromId, toId) =
  world[fromId].locationId === fromId && world[toId].locationId === toId
```

Grid-travel exits render in **Move**. Every other exit renders in **Here**,
including window-climb exits (both of which — `hallway2 ↔ living` and
`alley ↔ onebee` — are non-grid under this rule).

Window exits must keep being generated by `getExitsForRoom()` and must keep
respecting window state; only which panel they render in changes.

### 2. Move ordering

Sort grid-travel exits by `computeDirection(from.locationId, to.locationId)`
using the rank:

```
north = 0, east = 1, west = 2, south = 3
```

**The sort must be stable.** `Array.prototype.sort` is stable in every engine
this game targets, so a plain `sort` by rank is sufficient. Stability is what
keeps each intersection's "Head …" ahead of its "Step into the block …" —
verified above as already true in authoring order for all 224 pairs, with no
secondary sort key needed. Do not add one; do not re-derive the pair
relationship from label text.

Directions `up` and `down` cannot occur here (proven above). If a future street
node ever produces one, it must not crash the sort — give unknown directions a
rank after `south` rather than `undefined`.

### 3. Here ordering

Relocated exits render **first** in the Here panel, above the existing locked-
door notices, in their unmodified authoring order. They are not sorted.

They keep their `fmtDuration(exitMinutes(exit))` cost suffix and their existing
`actionButton` styling — the button is unchanged, only its parent moves.

### 4. Empty Move group

Add `id="moveGroup"` to the Move `.actions-group` div and hide it when it holds
no buttons, exactly mirroring `hereGroup`:

```
moveGroup.style.display = moveBox.children.length ? "" : "none";
```

Without this, every indoor room renders a "MOVE" heading above an empty row.
**42 of the game's 218 rooms are non-street rooms**, so this is the common case
indoors, not an edge case.

## Design decisions to make during implementation

1. **Where the classification helper lives.** It reads WORLD DATA but is
   consumed by RENDERING. Recommended: a small helper beside
   `getExitsForRoom()` in WORLD INTERACTION, since that function already owns
   "which exits does this room offer". Record the choice in the changelog.
2. **Whether `getExitsForRoom()` returns one list that each panel filters, or
   two lists.** Recommended: keep `getExitsForRoom()` returning one list
   (unchanged signature, unchanged window handling) and let each render
   function filter it. That keeps the window-exit generation in one place and
   makes the change provably additive.
3. **Whether the relocated exits get a visual separator** from the rest of the
   Here actions. Recommended: no separator for this pass — they are ordinary
   action buttons and the panel already mixes kinds. If they read as crowded in
   play, that is a follow-up, not this pass.

## Data / schema changes

None. No PLAYER STATE fields, no item schema, no room/container/exit schema
fields are added or changed. No `exits` array is reordered.

## In scope

- Classify every exit as grid travel or not, by the rule above.
- Render grid-travel exits in Move, sorted N/E/W/S by computed direction.
- Render every other exit — including window-climb exits — first in Here, in
  authoring order.
- Add `id="moveGroup"` and hide the Move group when empty.

## Explicitly out of scope

- **Reordering the Here panel's existing actions** (Rest, Sleep, Search,
  windows, vehicle, fishing, stove, fire, tree, container locks). Their order is
  unchanged; only the new exits are inserted ahead of them.
- **A compass-rose or spatial button layout.** Considered and set aside: most
  exits in the game have no direction at all, so a rose degrades badly in rooms
  with only non-directional exits. The wrapped row stays.
- **Any change to `exits` data**, labels, or `distanceM`. Issue #4 (stripping
  vestigial `distanceM` from 26 cross-Location exits) is adjacent but separate
  and is not a prerequisite.
- **Renaming the panels.** "Move" and "Here" keep their headings.
- Phone-viewport layout (#16) and map rendering (#19, #20) — untouched here.

## Sections touched

- **UI/RENDERING** — `renderMoveActionsPanel()`, `renderHereActionsPanel()`.
- **WORLD INTERACTION** — possibly one added helper beside
  `getExitsForRoom()`, per design decision 1.
- The static markup for the Move `.actions-group`.

No WORLD DATA, no PLAYER STATE, no SIMULATION, no ACTIONS behavior changes.

## UI changes

- Indoors, the Move section disappears entirely; room-to-room exits, stairs,
  building entrances, the fire escape and window climbs all appear at the top of
  Here.
- On a street, Move holds only travel, ordered North, East, West, South, with
  each intersection's "Head …" immediately followed by its "Step into the
  block …".
- Street rooms that contain a building entrance gain a Here section holding it
  (9 rooms in total; the other 167 street rooms still show no Here exits).
- No button label, cost, or styling changes.
